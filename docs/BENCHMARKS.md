# Замеры производительности Tessera

Все числа, на которые ссылается README, живут здесь вместе с условиями, при
которых они получены. Смысл файла в том, чтобы цифру можно было
перепроверить, а не поверить на слово: под каждой таблицей написано, какой
целью она снимается и какой командой воспроизводится.

## Откуда взялись 109x (и почему их больше нет в README)

До этого замера в README стояла таблица с ускорением до 109x и колонкой CPU,
где во всех четырёх строках стояло ровно `37 Mcells/s`. Одинаковое число при
четырёхкратном изменении размера поля - уже подозрительно, но объяснение
нашлось точное. Прогон того же стенда в **Debug**:

| Размер | CPU (Debug) | CPU (Release) |
|---|---|---|
| 256² | 37.60 Mcells/s | 271 Mcells/s |
| 1024² | 36.62 Mcells/s | 283 Mcells/s |
| 2048² | 37.33 Mcells/s | 281 Mcells/s |

Старая таблица снималась Debug-сборкой. `CpuLifeBackend` - это обычный
C++ цикл, и `/Od` замедляет его в **7.6 раза**. CUDA при этом почти не
меняется (ядро исполняется на устройстве, host-обвязка в общем времени почти
не видна): Debug дал 2367 Mcells/s на 1024², в старой таблице стоит 2366.

То есть 109x - не выдумка и не опечатка, а сравнение **заторможенного** CPU
с полноценным GPU. Как характеристика GPU оно бессмысленно: Debug никто не
поставляет.

Чтобы это не повторилось, `tests/benchmark` теперь печатает конфигурацию
сборки первой строкой, определяя её по `NDEBUG`, а не по имени пресета:

```
  build: Release/NDEBUG (оптимизированный)
  build: Debug (БЕЗ ОПТИМИЗАЦИЙ - CPU-число занижено примерно в 7 раз!)
```

## 1. CPU против CUDA, один чанк

**Что меряется:** один вызов `simulate()` на чанк заданного размера, правило
Конвея, 200 итераций. CPU-колонка - **однопоточная**: `CpuLifeBackend` не
использует ни потоков, ни SIMD, он считает один чанк от начала до конца одним
потоком. Многопоточность в движке даёт `TaskScheduler`, раздавая РАЗНЫЕ чанки
разным воркерам, - это отдельная таблица ниже.

Медиана трёх прогонов:

| Размер чанка | CPU (1 поток) | CUDA | Ускорение |
|---|---|---|---|
| 256² | 271 Mcells/s | 335 Mcells/s | 1.2× |
| 512² | 281 Mcells/s | 1085 Mcells/s | 3.9× |
| 1024² | 283 Mcells/s | 2281 Mcells/s | 8.1× |
| 2048² | 281 Mcells/s | 2967 Mcells/s | 10.6× |

Разброс между прогонами: CPU в пределах 1-2%, CUDA до 8% на крупных полях.

```bash
Test_benchmark 2048 200
```

Полезнее самого ускорения - точка окупаемости: на 256² GPU практически не
выигрывает, потому что запуск ядра и пересылка стоят дороже самой работы.
Разница начинает быть заметной от ~512².

## 2. Во что упирается CUDA (спойлер: не в вычисления)

Наивная проверка "не упёрлись ли в память устройства" даёт отрицательный
ответ. Ядро использует тайлинг в shared memory, то есть на клетку приходится
примерно чтение байта и запись байта:

```
2967 Mcells/s x 2 байта = 5.9 GB/s трафика к device-памяти
пропускная способность GDDR6 у 3060 Ti = 448 GB/s
занято: 1.3 %
```

Полтора процента - значит узкое место не здесь. Оно на **шине PCIe**:
`simulate()` синхронно копирует буфер в устройство и результат обратно на
КАЖДЫЙ вызов.

```
на итерацию (2048²):
  H2D  ext-буфер 2050² =  4 202 500 байт
  D2H  out-буфер 2048² =  4 194 304 байт
  итого                =  8.40 MB
время итерации         =  4 194 304 / 2967e6 = 1.41 мс
эффективная скорость   =  8.40 MB / 1.41 мс  = 5.9 GB/s
```

PCIe 4.0 x8 - это 15.75 GB/s теоретически; синхронные пересылки из
непристёгнутой (pageable) памяти обычно берут 50-60% пика, то есть 8-9.5 GB/s
практически. Полученные 5.9 GB/s - около двух третей достижимого, а сама
пересылка занимает примерно **две трети времени итерации**.

Косвенное подтверждение: во время прогона утилизация GPU по `nvidia-smi`
держится на **11-41%**, а не под 90%, как было бы при упоре в вычисления.

Отсюда два следствия, и оба стоит знать:

1. Числа в таблице 1 занижены относительно возможностей карты - в том числе
   потому, что шина работает на x8 вместо x16.
2. Правильное направление оптимизации здесь - не трогать ядро, а убрать
   пересылки: держать поле в device-памяти между шагами и копировать только
   то, что нужно показать. Частично это уже сделано (CUDA-GL interop,
   `simulateToGL`), но на Windows WDDM он откатывается на обычное копирование,
   потому что симуляция идёт в воркер-потоках без текущего GL-контекста.

**Чего этот раздел не утверждает:** что ядро оптимально. Он утверждает
только, что данным стендом производительность ядра измерить нельзя - его не
видно за пересылками. Для замера самого ядра нужен прогон с амортизированными
пересылками (одна H2D в начале, одна D2H в конце) или Nsight Compute; это ещё
не сделано.

## 3. Масштабирование пула потоков

**Что меряется:** тот же CPU-бэкенд, но много чанков, розданных по 12 воркерам
через `TaskScheduler`. Именно это видит движок, когда активна большая область.

| Сцена | CPU 1 поток | CPU 12 потоков | Ускорение |
|---|---|---|---|
| 1 × 64² | 272 Mcells/s | 175 Mcells/s | **0.64×** |
| 8 × 64² | 280 Mcells/s | 685 Mcells/s | 2.5× |
| 20 × 64² | 257 Mcells/s | 908 Mcells/s | 3.5× |
| 100 × 64² | 274 Mcells/s | 1215 Mcells/s | 4.4× |
| 300 × 64² | 272 Mcells/s | 1369 Mcells/s | 5.0× |
| 800 × 64² | 275 Mcells/s | 1441 Mcells/s | 5.2× |

```bash
Test_batch_benchmark
```

Две вещи, которые здесь важнее максимума:

- **На одном чанке пул медленнее в полтора раза** (0.64×). Это не дефект, а
  прямое следствие гранулярности: единица работы - целый чанк, поэтому один
  чанк = одна задача = один поток, а раздача и синхронизация добавляются
  сверху. По той же причине таблицу 1 (один чанк) нельзя пересчитать в
  "многопоточный CPU" умножением - пул физически не может ускорить ту строку.
- **Потолок около 5.2× на 12 логических потоках**, а не 12×. Ядер физически 6
  (SMT даёт остальные 6 логических), и упирается всё в общую очередь задач,
  которую разбирают все воркеры. Честный следующий шаг - очередь на воркер
  плюс work stealing.

## 4. Профиль кадра: demo/light

**Что меряется:** волновое поле 400×400 = **160 000 узлов** на канал, три
канала R/G/B, 12 потоков, сцена с призмой и лучом. Стенд разделяет источники
накладных расходов, поочерёдно включая нагрузку на поток рендера.

Среднее по 5 прогонам:

| | мс |
|---|---|
| `step()` ×3, рендер спит (базовая линия) | 2.92 |
| `step()` ×3, рендер только `snapshot()` | 4.63 |
| `step()` ×3, рендер полный | 5.37 |

Разложение накладных расходов (2.45 мс сверх базовой линии):

| Источник | мс | доля |
|---|---|---|
| ожидание на мьютексе поля | 1.71 | около двух третей (57-78% по прогонам) |
| конкуренция за пул потоков | 0.74 | около трети (22-43% по прогонам) |

Разброс между прогонами большой, поэтому в README стоит "около двух третей", а
не одно число: одиночный прогон здесь ничего не доказывает.

**Что означает вторая строка.** Это НЕ contention на мьютексе пула. Величина
считается как разница между "рендер только снимает копию" и "рендер ещё и
собирает вершины", а сборка вершин идёт через тот же `parallelFor` по тем же
12 воркерам. То есть это конкуренция за сами рабочие потоки: задачи рендера
занимают воркеров, которых ждёт физика. Лечится разделением пулов, а не
уменьшением числа захватов лока (проверено, см. ниже).

Поток рендера:

| | мс | доля CPU-кадра |
|---|---|---|
| `snapshot()` ×3 (копия 9 полей) | 0.22 | 23% |
| сборка вершин (160k узлов) | 0.73 | 77% |
| **итого CPU на кадр** | **0.94** | |

При vsync 60 FPS (16.67 мс на кадр) рендер занимает **5-7%** бюджета.
Важная оговорка: это CPU-часть, **без** `glBufferData` - загрузка в GL здесь
не меряется.

Zero-copy путь (`acquireView()` вместо `snapshot()`) убирает копию: кадр
рендера 0.62 мс вместо 0.94, физика выигрывает 0.18 мс (3%).


## 5. Отрицательный результат: батчинг постановки задач

Гипотеза была такая. `parallelFor` вызывается 4 раза за `step()` × 3 канала =
12 раз на шаг физики, и каждый вызов ставит по задаче на воркер через
`schedule()`, то есть **144 захвата мьютекса и 144 `notify_one` за шаг** - на
том же мьютексе, за который дерутся 12 воркеров и поток рендера. Выглядит как
очевидная цель: поставить все задачи за один захват.

Сделано (`schedule_n`, 144 захвата → 12), измерено честным A/B - два бинарника,
прогоны вперемешку, чтобы дрейф машины не выдал себя за эффект:

| | базовая линия `step()` |
|---|---|
| по задаче за раз | 3.102 мс |
| пакетом | 3.096 мс |

**0.17%, то есть ничего.** Изменение откачено.

Почему: захват неконкурентного мьютекса стоит десятки наносекунд, а один
`parallelFor` делает около 250 мкс полезной работы. Локи - порядка сотой доли
процента от работы, они физически не могли быть узким местом. Настоящая треть
накладных расходов - это конкуренция за рабочие потоки (см. раздел 4), и
батчингом она не лечится.

Первый же прогон "до/после" последовательно показал ухудшение на 8%, и только
чередование прогонов показало, что это дрейф машины, а не эффект.
