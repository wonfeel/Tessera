2D движок симуляций на C++/CUDA/OpenGL, распространяется по [лицензии MIT](LICENSE).
Мир разбит на чанки - симулируются только живые, симуляция и рендер работают в отдельных потоках,
а бэкенд симуляции (CPU или CUDA) подменяется за одним интерфейсом. Писал, чтобы разобраться с
потоками, тред-пулом, CUDA и OpenGL на практике, а не просто почитать.

**Задача:** симулировать практически бесконечное поле, обновляя только живые области, параллельно
на CPU/GPU и не роняя рендер.
**Решение:** разбить мир на чанки; считать живые на собственном тред-пуле; не давать вычислению и
коммиту пересекаться через фазовый барьер; гонять один и тот же код на CPU или CUDA-бэкенде;
вынести рендер в отдельный поток, чтобы тяжёлый шаг не съедал кадры.

Как устроена каждая часть - владение, фазовый барьер, жизненный цикл чанка - в
[архитектурных заметках](https://wonfeel.github.io/Tessera/architecture.html).

## Зачем я это написал

До этого у меня было поле цветов в консоли Windows, OpenGL-рендерер с нуля и первая попытка
«движка» без чанков и потоков, которая лагала. Это проект, где я исправил последнее и заодно
ответил себе на три вопроса: как разделить симуляцию и рендер по потокам, не словив гонки; как
написать тред-пул, который реально работает; и правда ли GPU ускоряет (правда, но только начиная
с некоторого размера - см. бенчмарк).

---

## Что умеет

- Чанковый мир - симулируются только живые чанки, состояние само активирует соседние при
  достижении их границ (глайдеры в «Жизни» пересекают границу чанка целыми).
- Симуляция параллельна на собственном тред-пуле; у рендера свой поток, поэтому тяжёлый шаг не
  дёргает картинку.
- Один интерфейс бэкенда (`ISimulationBackend`) - CPU и CUDA взаимозаменяемы, остальной движок не
  знает, что получил. CUDA-бэкенд использует тайлинг в shared memory, чтобы срезать обращения к
  DRAM.
- Рендер на гекс-сетке рядом с квадратной - для демок, которым нужны изотропные соседи (свет,
  червь).
- Встроено в базовый `Application`, поэтому достаётся каждой демке бесплатно: запись экрана (F9),
  экспорт GIF, ImGui-панели.

CUDA-GL interop (писать результат прямо в GL-буфер, минуя PCI-E) реализован, но на Windows WDDM
откатывается на обычное копирование - симуляция идёт в воркер-потоках, где GL-контекст недоступен.

## Бенчмарк

Правило Конвея, один чанк, 200 итераций, медиана трёх прогонов. Ryzen 5 5600 (6я/12п) +
RTX 3060 Ti, сборка **Release**. Колонка CPU - **однопоточная**: `CpuLifeBackend` не использует
ни потоков, ни SIMD, он считает один чанк одним потоком от начала до конца. Параллелизм по
чанкам - работа `TaskScheduler`, он меряется отдельно.

| Размер чанка | CPU (1 поток) | CUDA          | Ускорение |
|--------------|---------------|---------------|-----------|
| 256²         | 271 Мкл/с     | 335 Мкл/с     | 1.2×      |
| 512²         | 281 Мкл/с     | 1085 Мкл/с    | 3.9×      |
| 1024²        | 283 Мкл/с     | 2281 Мкл/с    | 8.1×      |
| 2048²        | 281 Мкл/с     | 2967 Мкл/с    | 10.6×     |

Интереснее самого ускорения - точка окупаемости: до ~512² GPU почти не выигрывает, потому что
запуск ядра и пересылка по PCI-E стоят дороже самой работы.

Этот стенд упирается **в пересылку, а не в вычисления**: ядро занимает всего ~1.3% пропускной
способности памяти карты, а копирование host↔device съедает около двух третей итерации. Полная
арифметика и разбор того, откуда в прежней версии таблицы взялись 109×, - в
[docs/BENCHMARKS.md](docs/BENCHMARKS.md).

Пул потоков, много чанков на 12 потоках: **5.2×** на 800 чанках и **0.64×** (медленнее!) на одном
чанке - один чанк это одна задача и один поток, пул там может только добавить накладных расходов.

Запустить самому: `Test_benchmark <размер_чанка> <итераций>` и `Test_batch_benchmark`.

## Сборка

CMake 3.20+ и Ninja, под Windows или Linux. CI собирает обе на каждый пуш.

**Windows** (Visual Studio 2022 / MSVC). Зависимости ([GLFW](https://www.glfw.org/),
[GLAD](https://glad.dav1d.de/), [GLM](https://glm.g-truc.net/),
[Dear ImGui](https://github.com/ocornut/imgui)) уже лежат в `libs/` - больше ничего ставить не нужно.

```bash
cmake --preset x64-release
cmake --build out/build/x64-release
```

**Linux** (GCC или Clang). Из системы берётся только GLFW - в `libs/` лежит его Windows-сборка;
GLAD, GLM и ImGui вендорятся и используются как есть.

```bash
sudo apt install ninja-build libglfw3-dev libgl1-mesa-dev xorg-dev
cmake --preset linux-release
cmake --build out/build/linux-release
```

CUDA опциональна: без неё собирается CPU-only, и CMake сам напишет, что выбрал:

```
-- CUDA found – GPU simulation backend enabled
-- CUDA not found – building CPU-only simulation backend
```

## Демки и тесты в этом репозитории

Маленькие демки, оставленные для разработки и тестирования движка. Полная интерактивная версия
каждой - в своём отдельном репозитории (см. выше):

```
Demo_life_minimal   Случайное поле + пушка Госпера (полная версия в HexLife).
Demo_light          Одно LightField, клик-плюк, без UI (полная версия в WaveLight).
Demo_cloth          Симуляция ткани на пружинной сетке.
```

Тесты в `tests/` headless, код возврата 0 = всё прошло:

```
Test_correctness    правило + парсер .rle, и побайтовое совпадение CPU и CUDA за 100 шагов
Test_propagation    глайдер должен пересечь границу чанка целым
Test_capture        детерминированный дамп GIF, регрессионный оракул
Test_benchmark      пропускная способность CPU vs GPU
Test_batch_benchmark  масштабирование пула: 1..800 чанков, 1 поток против 12
Test_light_frame_profile  куда уходит кадр: разделяет накладные расходы на
                    ожидание мьютекса поля и конкуренцию за пул потоков,
                    плюс сравнивает zero-copy путь рендера со снимком
Test_thread_safety  стресс тред-пула и чанк-стора, задуман под TSan
tests/light_field_* регрессия и бенчмарки волнового поля
```

Замеренный вывод всего перечисленного, вместе с железом и оговорками, лежит в
[docs/BENCHMARKS.md](docs/BENCHMARKS.md) - включая одну оптимизацию, которая не изменила
ничего, и разбор почему.

`Test_propagation` появился, когда выяснилось, что глайдеры «обрезаются» на границе чанка - тест
ставит глайдер у самой границы и проверяет, что он вышел с другой стороны в правильной форме и
позиции.

### Санитайзеры

Гонки, которые в этом движке реально были - вставка в чанк-стор под shared-блокировкой, старт
пула до выставления флага, потерянная побудка в shutdown - находились чтением кода, а этот способ
перестаёт работать сразу же, как перестаёшь читать. `Test_thread_safety` воспроизводит те же
сценарии, чтобы их проверял ThreadSanitizer. У MSVC его нет, поэтому только Linux; в CI гоняется
на каждый пуш:

```bash
cmake --preset linux-tsan
cmake --build out/build/linux-tsan --target Test_thread_safety
ctest --test-dir out/build/linux-tsan -R Test_thread_safety --output-on-failure
```

AddressSanitizer работает на обеих платформах: добавить `-DFE_ENABLE_ASAN=ON` к любому пресету.
